# Phase 4 — отчёт (DNS processing, records cache, rule-set snapshot)

Дата: 2026-07-22. Ветка: `claude/magitrickle-c-rewrite-phase-0-t7iwas`.
Go backend не изменён (recordsCache-оракул импортирует реальный пакет
`magitrickle/utils/recordsCache` без модификаций).

## Выполнено

- **Records cache** (`src/dns_cache/cache.c`, `include/magitrickle/dns_cache.h`)
  — построчный порт `utils/recordsCache/records.go`: domain→адреса
  (дедуп по точным байтам адреса, обновление deadline при повторной
  вставке), domain→alias (последняя запись побеждает, self-alias
  игнорируется), reverse-index alias→[domains] для BFS в
  `GetAliases` (включает домен сам по себе + все транзитивные CNAME-и,
  **не фильтруя по TTL** — точно как в Go, где эта асимметрия
  подтверждена чтением исходника). `GetAddresses` идёт по цепочке alias
  вперёд с защитой от циклов, возвращает первый узел с валидными
  адресами. `cleanup()` физически удаляет истёкшие адреса/alias-ы и сам
  domain-узел, когда он полностью пуст — воспроизводит поведение Go
  (два логически разных "map" в Go объединены в одну domain-запись, но
  cleanup-семантика проверена построчно против `records_test.go`).
  Hardening сверх Go (спец. §15): ограничение числа доменов
  (по умолчанию 65536) со счётчиком dropped при переполнении; на
  уже существующий домен новые адреса/alias всё равно принимаются.
  **Конкурентность**: без блокировок — кэш и матчинг живут исключительно
  на loop-потоке (D-17, ниже).
- **Rule-set snapshot** (`src/rules/snapshot.c`,
  `include/magitrickle/rulesnap.h`) — иммутабельный снимок групп: для
  каждой **включённой** группы строится один агрегирующий `mt_matcher_t`
  (OR по включённым правилам). Отключённые группы не входят в снимок
  вовсе (Go: `AddIPv4Subnet` для отключённой группы всегда no-op, значит
  строить для неё индекс бессмысленно — задокументировано в D-18).
- **DNS pipeline** (`src/dns/pipeline.c`,
  `include/magitrickle/dnspipeline.h`) — порт наблюдаемой части
  `dns.go` (`handleMessage`/`processARecord`/`processAAAARecord`/
  `processCNameRecord`): обрабатываются только успешные ответы
  (rcode=0), только записи из Answer-секции (A/AAAA/CNAME; остальное
  игнорируется), A/AAAA с неверной длиной rdata пропускаются с
  предупреждением (как в Go). Для каждой (группа, запись) пары —
  максимум одно действие через sink-callback вместо повтора
  Go-цикла по правилам (см. D-18: доказано состояние-эквивалентно).
  Sink в Phase 4 — заглушка (логирует уровнем INFO то, что в Phase 5
  станет реальным `ipset add`).
- **Демон** (`src/main/main.c`): создаёт кэш + pipeline + снимок
  правил из загруженного конфига, регистрирует 30-секундный таймер
  очистки кэша на loop, подключает pipeline к response-callback
  DNS-прокси. Контракт "AAAA всё ещё попадает в кэш/матчинг, даже если
  вырезается из ответа клиенту" — подтверждён эмпирически (см. ниже).

## Решения (decisions.md)

- **D-17** — без блокировок в hot-path: DNS-прокси, кэш и матчинг
  работают исключительно на одном `mt_loop`-потоке (следствие D-02), так
  что "атомарная публикация снимка" — это просто присваивание указателя.
  Спецификационное требование "no global lock in match path"
  удовлетворено по построению. Пересмотр — когда Phase 7 введёт рабочий
  поток для подписок (fetch), тогда публикация снимка будет
  маршализована на loop-поток через `mt_loop_post`.
- **D-18** — снимок матчит на уровне группы агрегированным OR вместо
  повтора Go-цикла (`break Rule` для A/AAAA, `continue Rule` для CNAME).
  Доказано аналитически: оба идиома всегда дают одинаковый **набор
  входных данных для действия** независимо от того, какое конкретно
  правило сработало (тот же IP/TTL для A/AAAA, тот же набор кэшированных
  адресов для CNAME) — значит итоговое состояние ipset идентично;
  единственная разница — Go может вызвать `AddIPv4Subnet` несколько раз
  избыточно для одного CNAME-события при совпадении нескольких правил в
  группе (идемпотентно, `Replace: true`); C схлопывает это в один вызов
  — именно такая дедупликация сетевых round-trip'ов явно поощряется
  спецификацией §16. Зафиксировано явно (не тихое расхождение).

## Проверки

- `make CFLAGS_EXTRA=-Werror` (host) — 0 warnings.
- `make test` — 12 бинарников (test_dns_cache: 21 тест, test_rulesnap:
  4 теста — новые в этой фазе), все Pass.
- `make sanitize` — ASan+UBSan, все Pass.
- `make static_analysis` — clang-tidy + cppcheck, 0 findings (заодно
  добавлены в анализ ранее пропущенные `dnstool.c`/`cachetool.c`).
- `make CROSS_COMPILE=mipsel-linux-gnu-` — core-слой (включая
  `dns_cache/cache.c`) кросс-компилируется чисто; `pipeline.c` требует
  PCRE2-слоя, кросс-сборка полного демона остаётся задачей Phase 8.
- **ASan/UBSan-стресс полного pipeline под нагрузкой**: смешанный
  UDP/TCP трафик (match + nomatch + AAAA + CNAME-цепочки, 200 правил,
  ~95 528 сработавших routing-действий за один прогон) — **0 ошибок**,
  чистое завершение по SIGTERM.
- **Differential**: новый cache-oracle (Go, импортирует реальный пакет
  `recordsCache` без изменений) против `mt-cachetool` — 19 команд
  сценария (basic A/CNAME, множественные адреса, обновление deadline,
  repoint alias, BFS fan-in, глубокая CNAME-цепочка, взаимный цикл,
  self-alias, неизвестные домены, `KNOWNDOMAINS`, expiry+cleanup,
  частичная просрочка) — **побайтово идентичны**. Сравнение намеренно
  структурное (presence/absence), а не по точным секундам TTL, так как
  два независимых процесса не могут быть тактированы синхронно по
  wall-clock — обоснование в комментариях `cache_oracle_go/main.go`.
- **Функциональные проверки на реальном демоне**:
  - совпадающий запрос → лог `would add to routing` с верным
    addr/ttl (300+3600=3900 — TTL записи + additionalTTL по умолчанию);
  - несовпадающий запрос → без действия;
  - CNAME-цепочка (3 хопа) → ровно одно действие на финальный A-ответ
    (via fan-in aliases), с верным адресом/TTL;
  - AAAA-запрос → клиенту `ancount=0` (вырезан), но в логе всё равно
    `would add to routing` с IPv6-адресом — **контракт "AAAA всё ещё
    входит в кэш/ipset, даже вырезанный из ответа" подтверждён**.
- **Soak (90 c, вне ASan)**: 500 правил, 100k уникальных имён,
  CNAME-цепочки длины 3, ~13.3k rps UDP (conc 30) + ~1.7k rps TCP
  (conc 10), **0 ошибок, 0 таймаутов** за 1.35M запросов. RSS: 2.8 MB
  на старте → плато **23.8 MB** за первые 5 секунд → идеально плоский
  все оставшиеся 85 секунд (`docs/c-rewrite/soak-c/rss.csv`). Рост
  кэша ограничен под непрерывной высокой кардинальностью трафика —
  критерий выхода Phase 4 выполнен.

## Нерешённое / перенесённое

- Настоящее сравнение "итогового состояния ipset" между Go и C
  недостижимо в этой песочнице (нет модуля ядра `ip_set`, см.
  phase-0-report — блокер для Phase 5); аналитическое доказательство
  state-equivalence (D-18) — единственно возможная проверка на данном
  этапе для CNAME multi-rule случая.
- Подписки (synthetic rule sets) не участвуют в снимке — только
  `mt_config_t.groups`; подключение — Phase 7.
- HTTP/Unix API ещё не существует, поэтому нет live-эндпоинта для
  инспекции состояния кэша/dropped-счётчика во время soak — оценивалось
  только по RSS и логам.

## Вход Phase 5

netfilter/netlink: ipset через libmnl (create/destroy/add/del/list c
таймаутами), iptables save/restore batching против тех же
fake-executable транскриптов, что и `utils/iptables/iptables_test.go`,
ip rule/route + аллокация mark/table, port remap, cleaner, netlink
watcher (link/addr). Именно здесь Phase 4 sink-заглушка получит
реальную реализацию (`ipset add`), что откроет путь к полноценному
end-to-end сравнению с Go в netns.
