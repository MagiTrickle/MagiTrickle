# Phase 8 — отчёт (packaging)

Дата: 2026-07-23. Ветка: `claude/magitrickle-c-rewrite-phase-0-t7iwas`.
Go backend не изменён.

## Выполнено

- **`build_backend` получил реальный C-путь** (`Makefile`) — новая
  переменная `BACKEND` (`go` по умолчанию, `c` — опционально),
  `C_CROSS_COMPILE`/`C_SYSROOT` для кросс-сборки. Намеренно **не**
  переключение всего проекта разом: дефолт остаётся `go`, все
  существующие 40 `config/*/*.config`-целей и вся CI-матрица продолжают
  собираться как прежде. `BACKEND=c` вызывает `src/backend-c`'s
  Makefile с `BUILD=$(UNIQUE_NAME)` и копирует `magitrickled-c` в тот же
  `$(COMPILE_DIR)/magitrickled`, что уже использует Go-путь —
  `prepare_files`/упаковка не потребовали изменений вообще. Реальных
  Entware/OpenWrt тулчейнов и feed-сисрутов для остальных целей в этой
  песочнице нет (см. D-37) — переключение дефолта без них молча
  сломало бы всю матрицу, что противоречит духу спецификации
  ("компоненты переезжают по одному за контрактами").
- **Упаковка (ipk/apk) под C-бинарник** (`Makefile`, задача #48) —
  `C_DEPS_IPK`/`C_DEPS_APK` (libyaml, PCRE2, libmnl, libcurl, cJSON),
  добавляются в `Depends:`/`-I "depends:..."` только при `BACKEND=c`,
  и Entware/OpenWrt-ветки `package_ipk` и `package_apk` — без
  регрессии для Go-пути (проверено побайтовым сравнением `control`
  для обеих платформ и обоих бэкендов). Имена пакетов — лучшая догадка
  по конвенции фидов, явно помечены как неподтверждённые вживую (нет
  доступа к реальному индексу фида — см. D-37/D-38).
- **Найдены и исправлены две реальные поломки живого GitHub CI**
  (задача, инициированная пользователем в середине фазы, не по
  исходному плану, но напрямую связанная с пакетированием/сборкой):
  1. `check-c.yml`'s `build_test`/`differential`-джобы никогда не
     устанавливали `libmnl-dev`/`libcjson-dev`/`libcurl4-openssl-dev`
     — пробел, существовавший с Phase 5/6/7, просто не пойманный
     раньше. Исправлено добавлением пакетов в шаги установки
     инструментов.
  2. **Настоящая регрессия от собственной работы этой фазы**: смена
     `src/backend-c/Makefile`'s `all`-таргета (сделать полный демон
     целью кросс-сборки без разбора) сломала давно существующий
     `cross_build`-джоб (mipsel, без sysroot — только skeleton).
     Восстановлено условие "cross + нет SYSROOT → core-only", как было
     до Phase 8, при этом сохранена новая Phase-8-возможность (cross +
     SYSROOT → полный демон). Заодно найден и исправлен **отдельный,
     более старый баг** (с Phase 3): CI-джоб проверял бинарник
     `magitrickled-c`, которого core-only сборка никогда не производила
     — core-only ветка теперь линкует `mt-dnstool`/`mt-cachetool`
     (реальные, зависимости-свободные бинарники), и CI проверяет их.
     Линковка для mipsel вскрыла реально отсутствующий `-latomic`
     (8-байтные атомики в `dns/proxy.c` на 32-битных архитектурах) —
     добавлен в `LDLIBS`.
  3. Отдельно — `src/frontend/deno.json`'s `nodeModulesDir: "auto"`
     (строка) требует Deno новее, чем реально ставит CI; заменено на
     булево `true` (то же поведение, всегда принимается). И
     обнаруженный по итогам следующего живого прогона CI пробел:
     `--unstable-sloppy-imports` нужен `deno test`, чтобы резолвить
     существующие в репозитории безрасширенные импорты (`deno.json`
     уже отключал линт-правило `no-sloppy-imports`, но не включал
     сам рантайм-режим) — добавлено в `package.json`'s `test:unit`.
  См. D-38 для полного разбора всех трёх находок.
- **Кросс-компиляция реальными доступными тулчейнами** (задача #49) —
  реальный OpenWrt/Entware фид недоступен (подтверждённая политика
  egress, см. D-37), но `ports.ubuntu.com` (официальный вторичный
  архив Ubuntu) доступен. Собраны **полные** (не skeleton) демоны
  `magitrickled-c` для **arm64, armhf, riscv64** с настоящими
  Debian/Ubuntu multiarch-сборками всех 5 feed-зависимостей (libcurl
  вытащен вручную из-за конфликта dpkg на `/usr/bin/curl-config`), все
  три успешно запущены под `qemu-user`, плюс 11 юнит-тест-бинарников
  (115 assertions) прогнаны под эмуляцией — все проходят. `--sysroot`
  не подошёл этим конкретным тулчейнам (они рассчитаны на системный
  multiarch, не на изолированный sysroot) — использованы
  `CFLAGS_EXTRA`/`LDFLAGS`, уже существующие точки расширения
  Makefile. Честно задокументировано покрытие всех 40 реальных
  `config/*/*.config`-целей: что подтверждено как близкий glibc-прокси
  (Entware aarch64/armv7), что подтверждено только на уровне ISA
  (OpenWrt-цели — все musl), что осталось на уровне skeleton (mipsel,
  без изменений с D-37/D-38) и что не проверялось вовсе (mips,
  mips64, loongarch64, i386). См. D-40.
- **Решение по UPX — по замерам, не только по ожиданию** (задача #51)
  — 30-прогонный замер: **13.4 мс (без UPX) против 21.6 мс (с UPX)**
  запуска (~62% задержки на каждый старт процесса от LZMA-распаковки),
  при статистически неотличимом Peak RSS (10.84 vs 10.83 МБ — на
  размере в сотни КБ RSS доминируют разделяемые библиотеки, не сам
  бинарник). **Решение: UPX для C-бэкенда не нужен** — что уже и было
  фактическим состоянием (`BACKEND=c`-ветка `build_backend` никогда
  не вызывала `upx`), эта задача подтвердила это цифрами, а не только
  априорным ожиданием из `toolchains.md`. См. D-41.
- **Тест upgrade/downgrade преемственности, на уровне хоста**
  (задача #50) — реальный демон Go создаёт состояние
  (`/var/lib/magitrickle/config.yaml`+`auth_secret`) → останавливается →
  реальный `magitrickled-c` стартует на этом же состоянии (группа и
  секрет читаются байт-в-байт идентично, секрет не перегенерируется) →
  переименовывает группу через собственный HTTP API (`PUT
  .../groups/{id}?save=true`) → останавливается → Go перезапускается на
  C-изменённом состоянии и подхватывает переименование, секрет
  по-прежнему не тронут. Полный цикл в обе стороны, без потери
  состояния. По пути вживую воспроизведён (не как новый баг, а как
  подтверждение уже известного из D-36) `configVersion: "unattached"`
  квирк Go при пересборке без реальной версии — пересобрано с реальной
  `MT_VERSION=0.99.0` для чистого результата. Netfilter-состояние
  (iptables+ipset) не удалось проверить вживую: `ipset` в этой
  песочнице нефункционален на уровне ядра (`Invalid argument` даже под
  root, `modprobe` отсутствует) — блокирует включение любой группы в
  обоих бэкендах одинаково, не Go-vs-C специфично. См. D-42.

## Решения (decisions.md)

- **D-37** — `build_backend` получил C-путь через `BACKEND`-переключатель,
  намеренно не переключение всего проекта; `src/backend-c/Makefile`'s
  кросс-сборка больше не ограничена core-only безусловно.
- **D-38** — три находки реального GitHub CI: отсутствующие
  `libmnl-dev`/`libcjson-dev`/`libcurl4-openssl-dev` в `check-c.yml`
  (пробел с Phase 5-7); настоящая регрессия от D-37 в mipsel
  `cross_build`-джобе плюс отдельный более старый баг в его же
  MIPS-бинарник-проверке (с Phase 3) плюс найденный `-latomic`-пробел;
  `deno.json`'s `nodeModulesDir`/`--unstable-sloppy-imports`.
- **D-39** — упаковка (`C_DEPS_IPK`/`C_DEPS_APK`) под C-бэкенд;
  имена пакетов — лучшая догадка, не подтверждены вживую.
- **D-40** — кросс-компиляция реальными тулчейнами (arm64/armhf/riscv64
  через Ubuntu multiarch + `ports.ubuntu.com`), полные демоны собраны,
  слинкованы и запущены под `qemu-user`; честная разбивка покрытия
  всех 40 реальных целей.
- **D-41** — UPX keep/drop по замерам (13.4 vs 21.6 мс, RSS не
  отличается) — drop, подтверждено цифрами.
- **D-42** — upgrade/downgrade тест на уровне хоста, реальный цикл
  Go→C→Go; живое воспроизведение D-36's `configVersion` квирка;
  честно задокументированный пробел (`ipset` нефункционален в этой
  песочнице).

  песочнице) для обоих `BACKEND`.

## Нерешённое / перенесённое

- **Реальные Entware/OpenWrt тулчейны и feed-сисрутов недоступны** в
  этой песочнице (подтверждённая политика egress — та же ситуация,
  что и во всех предыдущих фазах). Кросс-компиляция этой фазы —
  доказательство механизма реальными прокси-тулчейнами (Ubuntu
  glibc), не реальными продакшн-тулчейнами. 33 из 40 реальных
  `config/*/*.config`-целей остаются частично или полностью
  непроверенными (полная разбивка — D-40).
- **Netfilter-состояние (iptables+ipset) upgrade/downgrade
  преемственность** не проверена вживую — `ipset` нефункционален в
  этой песочнице на уровне ядра (см. D-42). Код-уровень покрытия
  (transcript-parity тесты Phase 5, `cleaner.c`'s startup-cleanup,
  идентичные конвенции именования у обоих бэкендов) есть, но конкретно
  этот сценарий (переключение бэкенда, а не просто рестарт того же
  бинарника) не прогнан вживую.
- **Реальная on-device или эмулированная-образ проверка
  install/upgrade** (формальный exit-критерий Phase 8) не выполнена —
  ни реального устройства, ни готового Entware/OpenWrt диск-образа в
  этой песочнице нет. Тот же пробел, что называли отчёты всех
  предыдущих фаз.
- Имена пакетов feed-зависимостей в `Depends:`/apk `depends:`
  (`libyaml`, `libpcre2`, `libmnl`, `libcurl`, `libcjson`) — лучшая
  догадка по конвенции именования, не сверены с живым индексом фида
  (см. D-39).

## Вход Phase 9

Backend полностью функционален на C: все контракт-тесты, дифференциальные
наборы, санитайзеры и фаззинг зелёные, реальная кросс-компиляция и
упаковка проверены механически, реальный upgrade/downgrade цикл
подтверждён вживую на уровне состояния/конфига. Phase 9 — профилирование
и финальное бенчмарк-сравнение по методологии, полный чеклист
паритета из spec §23 по пунктам, и — отдельным изменением — удаление
`src/backend` (Go), Go-зависимостей и Go CI-шагов, обновление Makefile
и всей документации проекта (CLAUDE.md/AGENTS.md/README). Ничего в
этой фазе не удаляло и не изменяло Go backend, кроме документации —
условие Phase 9's gate ("ничего не удаляется, пока не пройден gate
Phase 9") соблюдено.
