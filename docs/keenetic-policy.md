# Фильтр устройств по политике Keenetic

Функция существует только в Entware-сборках с суффиксом `_kn`.
Она выбирает, к каким устройствам применяются **обычные** правила MT.
Она не является маршрутом назначения, не заменяет группы/подписки,
не создаёт политики Keenetic и не назначает их клиентам.

## Настройки

По умолчанию фильтр выключен: поведение прежнее. После включения выбираются
существующая политика Keenetic и один из режимов:

- `include` — обрабатывать только устройства выбранной политики;
- `exclude` — не обрабатывать устройства выбранной политики, обрабатывать остальные.

Изменения вступают в силу после «Сохранить». Устройства вне области MT не
блокируются: их трафик остаётся под управлением штатной маршрутизации Keenetic.
Списки доменов, подсетей, приоритеты групп/подписок и профили маршрутов MT
работают как прежде внутри выбранной области.

Сохраняется системный ID (`Policy0`), не отображаемое имя и не `mark`.
Повторяющиеся имена различаются ID. При удалении политики выбор не сбрасывается
на первую доступную. Выключение фильтра возможно и при недоступном RCI.

```yaml
app:
  keeneticPolicy:
    enabled: false
    policyId: ""
    mode: include
```

В старой конфигурации отсутствие блока означает выключенную функцию.
Обычная сборка не читает/не сериализует этот блок и не регистрирует API ниже.
Импорт такой конфигурации в обычную сборку не включает фильтр.

## Backend API (`_kn`)

На API действуют обычные правила доступа приложения, в том числе авторизация
WebUI при её включении. Браузер никогда не обращается к RCI непосредственно.

`GET /api/v1/keenetic/policies` возвращает нормализованный список:

```json
{"policies":[{"id":"Policy0","name":"VPN","available":true}]}
```

Отсутствующая/ещё не назначенная метка делает элемент `available:false`.
Нулевая метка валидна. `GET /api/v1/keenetic/policy` возвращает:

```json
{
  "settings":{"enabled":false,"policy_id":"","mode":"include"},
  "runtime":{"state":"disabled"}
}
```

`PUT /api/v1/keenetic/policy` принимает **непосредственно** объект из трёх полей:

```json
{"enabled":true,"policy_id":"Policy0","mode":"include"}
```

Возможные состояния runtime: `disabled`, `applying`, `ready`, `unavailable`,
`error`. HTTP 200 подтверждает принятие и сохранение настройки; при асинхронной
перестройке таблиц нужно смотреть runtime. Поле `reason` уточняет ошибку.
Невалидный запрос — 400; исчезнувшая/неготовая политика и конкурирующее
сохранение — 409; недоступный RCI — 502; переполненная очередь — 503.
Ошибка записи конфигурации — 500 с `code:"PERSISTENCE_FAILED", applied:true`
и актуальными settings/runtime: настройка уже принята в память, сохранение
можно повторить. Это **не** подтверждение успешного применения правил ядром.

## Получение и применение

RCI читается только из backend через фиксированный read-only URL
`http://127.0.0.1:79/rci/show/ip/policy`. HTTP redirects и proxy отключены.
Сетевой запрос выполняется отдельным коалесцирующим worker, не в DNS-loop:
connect timeout 500 мс, полный timeout 2 с, ответ до 1 МиБ, до 256 политик,
до 16 ожидающих HTTP-запросов. Большие/повреждённые ответы отклоняются целиком.
Нет shell-команд, `grep`, сохранённых в конфигурации меток или передаваемых
клиентом URL. HTTP 401/403 от RCI считается недоступностью; токен локального
RCI-прокси в этой версии не настраивается.

При выключенном фильтре нет фоновых запросов RCI. Список запрашивается явно
для селектора. При включённом фильтре backend сверяет метку каждые 15 секунд,
а включение/сохранение проверяет её свежим запросом. При старте с включённой
настройкой область MT закрыта до первого успешного разрешения метки.
Исчезновение политики/ошибка RCI переводит фильтр в `unavailable`; нет
неявного перехода к обработке всех устройств. Срок обнаружения изменения
ограничен интервалом опроса и временем запроса/применения.

В `mangle/PREROUTING` единый gate проверяет исходную маркировку Keenetic
с маской `0x0fffffff` **до** прохода через правила MT. Пропущенный пакет
попадает в общую упорядоченную цепочку групп/подписок. Проверка политики
не повторяется после каждого `MARK`, иначе первая группа испортила бы
классификацию следующих. Ответные пакеты и назначения на сам роутер
не входят в эту цепочку. Последнее сохраняет исходную метку до проверки
в `nat/PREROUTING` перед DNS DNAT MT.

Для исключения локальных назначений используются обычные `-d IP/32` и
`-d IP/128`: backend получает адреса интерфейсов через `getifaddrs`, включая
loopback, отдельно для IPv4/IPv6 и без дубликатов. Расширение `addrtype` не
требуется: на Keenetic с iptables 1.4.21 оно может отсутствовать в ядре, даже
если userspace принимает его синтаксис. Это список **назначенных интерфейсам
адресов**, а не проверка всех возможных маршрутов типа `local`.

Адреса пересчитываются при перестройке правил; события изменения адреса,
интерфейса или потери netlink-уведомлений запрашивают существующий committer.
Изменения собственных маршрутов MT не запускают такую перестройку повторно.
До разрешения метки политики gate содержит безусловный `RETURN` и не требует
получения адресов. Ошибка получения адресов у активной политики остаётся
ошибкой применения, а не превращается в разрешение обработки всего трафика.

Для filter/FORWARD и NAT используются дополнительные проверки connmark
маршрута MT: совпадение общего destination ipset само по себе не даёт MT
права обрабатывать исключённое устройство. Существующие правила записи
маркировки MT не изменены, новые служебные биты не выделяются. Полностью
выключенный фильтр не добавляет ни gate, ни guards.

Перестройка использует существующий netfilter committer и восстановление
после `netfilter.d`. Включение, выключение, смена режима и метки вызывают
полную согласованную перестройку MT-цепочек. Они не удаляют чужие цепочки.
Это не транзакция сразу через IPv4/IPv6: ошибка отдельного семейства
показывается как `error`, существующий committer повторяет применение.

## Границы гарантий и проверка на Keenetic

**Базовая проверка на устройстве подтверждена 2026-10-11:** после исправления
`7782532` пользователь сообщил об успешной работе политик и маршрутизации
трафика на своём Keenetic. Ранее на этом устройстве проверены iptables и
ip6tables 1.4.21: `conntrack --ctdir REPLY` работает, `addrtype` недоступен.
Это подтверждение запуска и рабочего пользовательского сценария, а не
отметка о прохождении каждого пункта расширенного чек-листа ниже.

**Уже установленные соединения могут сохранять прежний маршрут/DNAT до
переподключения.** Глобальная очистка conntrack намеренно не выполняется.
Фильтр — не firewall/kill switch. DNS-cache/ipset остаётся общим:
неперехваченный клиент, самостоятельно обращающийся прямо к порту DNS-сервера
MT, может пользоваться его DNS-ответами, но это не даёт ему обходить
пакетный фильтр маршрутизации.

Автоматические тесты проверяют генерацию/порядок правил и модель пакетов,
реальный локальный HTTP API с fake RCI, конфигурацию, оба режима и ошибки.
Они **не доказывают** поведение конкретной версии KeeneticOS, аппаратного
offload и места установки policy mark. Для проверки конкретной прошивки
и последующих регрессий сохраняется расширенный чек-лист:

1. Исходный policy mark доступен на входе MT gate в PREROUTING для IPv4
   и включённого IPv6. Доступны `mark`, `connmark`, `conntrack`
   в iptables/ip6tables; `addrtype` не требуется. При отсутствии модуля должна
   быть видимая ошибка применения, а не молчаливое отключение ограничения.
2. Два клиента (в политике и вне её), одно назначение из группы/подписки:
   include/exclude/off, DNS override on/off, новый TCP и UDP поток.
3. Пересекающиеся группы/подписки с разными приоритетами; повторный пакет
   соединения, ответы, собственный трафик роутера, оба семейства адресов.
4. Перезапуск MT и роутера, пересоздание/удаление политики, перенос клиента,
   смена mark, недоступный порт 79, netfilter.d и восстановление RCI.
5. Изменение IPv4/IPv6-адреса локального интерфейса: исключение в MT gate
   должно обновиться; DNS-пакет к локальному адресу сохраняет метку Keenetic,
   даже если адрес также попал в группу или подписку MT.

## Изоляция пакетов

Root Makefile выводит backend `ENTWARE_KN=1` и frontend `VITE_ENTWARE_KN=1`
только из `PLATFORM=entware` и `TARGET=..._kn`. Backend исключает policy
модули, поля и маршруты на этапе компиляции. Vite разрешает platform alias
либо в настоящий компонент (со своим API и переводами), либо в пустой
компонент без импортов. Это не скрытие через runtime-флаг/CSS.

По умолчанию frontend/stamps раздельны для каждой пары PLATFORM/TARGET.
Даже при явно переиспользованном `FRONTEND_OUT_DIR` проверяется маркер
параметров сборки; пакет копирует только соответствующий frontend.
CI-джобы SDK изолированы и явно экспортируют frontend в ожидаемый ими `dist`.
`tools/tests/keenetic_policy_isolation.py` проверяет реальные бинарники и
production bundles, а package_identity — отдельные пути пакетов и отсутствие
переноса KN payload в обычный Entware/OpenWrt.

Регрессия недоступного `addrtype`: `test_keenetic_policy_addresses` заменяет
только границы libc/iptables, отвергает это расширение и проверяет запуск,
оба режима, адреса/дубликаты, сбой перечисления и отключение фильтра.
`test_rule_priority` проверяет локальные назначения реальными адресами пакета,
не синтетическим флагом. `test_route_recovery` проверяет обновление по событиям.
Существующий `check-netfilter.yml` дополнительно проверяет scoped DNS rebuild
на настоящем ядре в отдельном namespace для legacy и nft frontends. Эти тесты
не заменяют проверку устройства с конкретной прошивкой Keenetic.

Перезагрузка конфигурации отдельно проверяется в `test_profiles_reload`:
пустые, одиночные и многозаписные группы/подписки в разных сочетаниях,
частично выполненное применение, точное восстановление старых runtime-флагов
и повторная перезагрузка после ошибки. Размеры старых реестров фиксируются
под netfilter-блокировкой и одинаково используются при выделении памяти,
сохранении состояния, освобождении и откате; подавления статического анализа
для этого пути нет.

Для политик используются существующие `check-c.yml`, `check.yml`,
`check-packaging.yml` и `check-netfilter.yml`; выпуск пакетов остаётся в
`build.yml`. Отдельного policy-workflow и временных source/dependency/apply
workflows в итоговой ветке нет. Регрессионные тесты остаются частью обычного
CI, а не заменяются ручной проверкой на одном роутере.
