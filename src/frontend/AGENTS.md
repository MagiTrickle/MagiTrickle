# Frontend AGENTS.md

Инструкции для `src/frontend/`, дополняющие корневой [AGENTS.md](../../AGENTS.md).
Общие ограничения проекта, контракты backend и правила Git продолжают действовать.
Пути ниже указаны относительно `src/frontend/`, если не оговорено другое.

Цель — развивать существующий интерфейс MagiTrickle: переиспользовать компоненты,
сохранять понятное поведение и выполнять конкретную задачу пользователя.

## 1. Перед изменениями

Проверь запрос, ветку и `git status`; сохрани чужую работу. Найди ближайший
сценарий Groups/Subscriptions/Settings, прочитай компонент, владельца состояния
и тест. «Как в группах» означает проверку исходников и фактического расположения,
а не подбор похожего padding.

Делай минимальное законченное изменение без потери обработки ошибок и данных.
Не добавляй попутный редизайн, обновление зависимостей и переработку CI.
Явно запрошенный дизайн меняй в заданных пользователем границах.

## 2. Стек и структура

Стек: Svelte 5, TypeScript, Vite, Bits UI, Valibot, Lucide. Версии — в `package.json`
и lock-файле. Не дублируй UI/state/DnD новым фреймворком.

| Ответственность                  | Расположение                                |
| -------------------------------- | ------------------------------------------- |
| Запуск и общие стили             | `src/main.ts`, `src/app.css`                |
| Авторизация и начальная загрузка | `src/App.svelte`                            |
| Навигация и внешний layout       | `src/components/layout/AppLayout.svelte`    |
| Общие Save/Add/Import/Export     | `src/components/layout/PageControls.svelte` |
| Общие UI-компоненты              | `src/components/ui/`                        |
| Экраны и операции функций        | `src/modules/`                              |
| Общие реактивные данные          | `src/data/`                                 |
| Типы и схемы                     | `src/types.ts`                              |
| HTTP, уведомления, helpers       | `src/utils/`                                |
| Перетаскивание                   | `src/lib/dnd/`                              |
| Проверки                         | `tests/unit/`, `tests/e2e/`                 |

Разметку и UI-обработчики держи в компонентах, операции состояния — у его владельца.
Чистые преобразования, валидацию и построение payload размещай в обычных `.ts`.
Модули с runes вне компонентов используют `.svelte.ts`. Не создавай лишние слои
и универсальные фабрики без конкретной необходимости.

## 3. Переиспользование

Перед новым элементом проверь существующие компоненты в `src/components/ui/`:

- `Button.svelte` — обычные кнопки и маленькие действия с иконкой.
- `Select.svelte` — выбор с описаниями, группами вариантов и собственным trigger.
- `RouteSelect.svelte` — общий выбор прямого интерфейса или профиля.
- `Tooltip.svelte`, `DropdownMenu.svelte`, `Switch.svelte`, `Checkbox.svelte`.
- `GenericDialog.svelte` и диалоги модулей — образцы работы с диалогами.
- `Placeholder.svelte` — loading/empty/error и действия повтора.
- `icons.ts` — именованные иконки действий. Не заменяй их emoji или новым набором.

Пагинация — `src/components/Pagination.svelte`, уведомления/overlay —
`src/utils/events.ts`. `PageControls` владеет Save/Add и мобильным размещением;
его snippet `search` может содержать описание. Не дублируй эти механизмы.

Используй существующие props/callbacks/snippets; расширяй совместимо с проверкой
потребителей. Общего `Panel.svelte` нет: `GroupPanel`, `SubscriptionPanel`,
`ProfilePanel` различаются логикой. Переиспользуй примитивы; не привязывай профили
к store групп. Общий компонент выделяй при реальном повторении ответственности.

## 4. Svelte и TypeScript

- Новый код: `<script lang="ts">`, тип `Props`, `$props()`, `$state`, `$derived`,
  callbacks и snippets. `$bindable` — для намеренного двустороннего binding.
- Производные значения вычисляй; не синхронизируй несколько копий флага эффектами.
  `$effect` нужен для побочного эффекта, не для вычисления валидности или скрытого autosave.
- Типизируй события, props и payload. Внешние данные проверяй через существующие
  схемы/validators: cast не заменяет runtime-проверку. Не скрывай проблему новыми
  `any`, `@ts-ignore` и необоснованными приведениями.
- У timers, observers, подписок и обработчиков должны быть владелец и очистка.
  DOM используй для фокуса, измерений и DnD; данные формы храни в состоянии.
- Комментарии объясняют причины и контракты; обновляй их вместе с поведением.

Старый API (`GenericDialog` и другие) учитывай без попутной массовой миграции.

## 5. Владение состоянием и списки

Groups/Subscriptions создают stores во view, передают их через Symbol context
и вызывают `mount()`/`destroy()`. Профили используют состояние модуля для черновика
между вкладками. Следуй модели изменяемой функции.

Различай серверные данные, draft, baseline и временное UI-состояние.
Фоновая загрузка не должна затирать ввод. Черновик в памяти не означает сохранение
после reload или на диск. Не разделяй изменяемые вложенные массивы draft и baseline.

Используй методы store, `ChangeTracker` и необходимый `markDataRevision()`:
изменение видимого массива не должно оставлять устаревшие поиск, дубликаты и валидацию.
Ключ строки — ID или уникальное имя интерфейса внутри профиля. Индекс служит номером.
Порядок интерфейсов значим: не сортируй массив ради сравнения/сериализации.

## 6. API и сохранение

Используй `src/utils/fetcher.ts`: он выбирает API base, добавляет авторизацию,
обрабатывает 401/403 и создаёт `HttpError`. Не дублируй это в компонентах
и не хардкодь адрес роутера.

Схемы находятся в `src/types.ts`; построители payload — в
`src/modules/groups/group-payload.ts`, `src/modules/subscriptions/subscription-payload.ts`
и helpers соответствующей функции. Сохраняй различие частичного обновления
и полного упорядоченного замещения. Не отправляй все правила ради одного поля
и не обходи конфликт baseline полной перезаписью коллекции.

Проверяй ввод до запроса: ID, дубликаты, обязательные поля и ограничения backend.
Лимит UTF-8 в байтах не равен числу символов input. Не удаляй отсутствующие ссылки
молча ради успешного сохранения; не мутируй исходные данные при построении payload.

Контракт профилей:

- Без изменений и отложенной записи Save недоступен.
- Валидный изменённый черновик можно сохранить. Busy и невалидность блокируют
  повторный запрос; причина объясняется существующими средствами UI.
- Успешный PUT принимается после проверки канонического ответа: обновляются
  серверные данные и baseline, снимается dirty.
- При отклонении, сетевой ошибке или некорректном ответе черновик сохраняется;
  успех и применение изменений не предполагаются.
- HTTP 500 с `code: "PERSISTENCE_FAILED"`, `applied: true` и полной валидной
  коллекцией подтверждает применение в памяти, но не запись на диск.
  Прими подтверждённые данные, сохрани `persistencePending` и Save для повтора.

Обычный 500/409 не подтверждает применение. Не сбрасывай отложенную запись
в `finally`. Groups/Subscriptions используют тот же принцип через
`src/utils/applied-save.ts`.

`profiles.list` — принятые определения; `profiles.draft` — работа редактора.
`RouteSelect` использует `profiles.list`, поэтому несохранённый профиль не должен
попадать в доступную конфигурацию других разделов.

Сохраняй защиту от повторного PUT и запоздалого GET, способного затереть новое
подтверждение. Busy снимай в `finally`, baseline меняй после подтверждения.
Refetch после каждого действия не заменяет корректную работу с состоянием.

## 7. Уведомления и ошибки

Общую ошибку запроса уже показывает `fetcher` через `toast`. Не дублируй её в
`catch` компонента и не создавай новые баннеры. Дополнительное сообщение нужно
для другого факта, например повтора записи уже применённых изменений на диск.

Loading/empty/error/Retry оформляй через `Placeholder`, ввод — существующей
валидацией. Локальная операция не требует полного overlay. Успех сообщай после
завершения операции. Обработка ошибки должна сохранять draft и снимать busy;
пустой `catch` не должен скрывать необработанную ошибку.

## 8. Стиль, размеры и адаптивность

Образцы — `GroupPanel`, `RuleRow`, `SubscriptionPanel`, `SubscriptionRuleRow`.
Используй токены `src/app.css`, `--font`, существующие иконки, поля, радиусы,
чередование строк и состояния кнопок. Не добавляй декоративные полоски, лишние
карточки, новую палитру, градиенты и пояснения к очевидным действиям.
Существующие эффекты общих компонентов сохраняй.

При сравнении различай padding страницы/шапки/строки, gap, ширину ячейки и размер
кнопки с padding/border. У строк `RuleRow` и профилей справа `0.1rem` на desktop
и `0.35rem` до `700px`; у шапки панели — `0.5rem`. Значения не взаимозаменяемы.
После изменения образца сверяй актуальный CSS и положение элементов в браузере.

Предпочитай scoped CSS. Общие стили меняй у владельца с проверкой потребителей;
не переопределяй глобальные селекторы Bits UI ради панели. Поздний shorthand
`padding` может отменить `padding-right`.

Сохраняй `min-width: 0`, `minmax(0, 1fr)` и принятые переносы/ellipsis.
Ячейка вмещает всю кнопку; не маскируй ошибку обрезанием и `overflow: hidden`.
Основной breakpoint — `700px`, у `PageControls` также `570px`: сохраняй его
резерв места для Save/Add и не вводи близкие глобальные breakpoints без необходимости.

## 9. Решения пользователя по Settings и профилям

### Структура и оформление

- `SettingsPanel` — набор обычных секций с заголовками. Профили — одна секция;
  другие настройки добавляются по своим задачам. Второй уровень вкладок
  ради единственного раздела профилей не возвращай.
- Редактор секции владеет своей загрузкой, изменениями и сохранением.
  Сохраняй семантический заголовок и `aria-labelledby`.
- Заголовок профилей оставляй без декоративной полоски и описания под ним.
  Заголовок раздела не должен быть мельче названия профиля. Принятая типографика:
  `600 1.3rem var(--font)`, как у названия профиля.
- Название профиля редактируется в шапке, как у существующих панелей.
  Подсказка пустого названия — placeholder; доступное имя input сохраняется.
- Связи показывай компактно: общая иконка `Link`, количества групп/подписок
  и подсказка. Отдельную заметную подпись Used by не возвращай.

### Добавление и действия

- Новый профиль имеет пустое название и пустой массив интерфейсов. Не подставляй
  первый интерфейс, рекомендуемый резерв или пример автоматически.
- Add interface находится среди действий шапки профиля. Пользователь открывает
  существующий Select и явно выбирает интерфейс; открытие страницы ничего не добавляет.
  Цвет триггера по умолчанию — `var(--text-2)`, как у соседних кнопок.
- Исключай из вариантов дубликаты и `blackhole`. После добавления сбрасывай
  кандидата picker, чтобы ранее удалённый интерфейс можно было добавить снова.
  Если вариантов нет, действие недоступно с пояснением.
- В редакторе профилей нет Cancel. Не возвращай кнопку из-за оставшейся функции
  сброса или устаревшего комментария. Это не запрещает Cancel в других диалогах.
- Используемый профиль нельзя удалить до переназначения ссылок. Сохраняй
  объяснение и проверку backend; использование нельзя определять только по
  данным текущей открытой вкладки.

### Строки и порядок

- Строка: grip, номер, интерфейс с описанием, удаление. Шапка и terminal-строка
  соответствуют той же сетке.
- Номер берётся из текущего индекса и обновляется после перестановки/удаления.
  Не возвращай колонку Priority и подписи Primary / Backup N.
- Образец нумерации — `SubscriptionRuleRow`. У `RuleRow` групп есть grip,
  но последовательных номеров сейчас нет; не меняй группы ради этой терминологии.
- Используй общий `src/lib/dnd/` и grip. Видимые кнопки со стрелками не добавляй;
  сохраняй клавиатурное Alt+↑/↓ у профилей.
- Drop ограничен scope и ID профиля: нельзя случайно перенести интерфейс
  в другой профиль. Позиции до/после строки должны давать ожидаемый порядок.
- `blackhole` — последняя неактивная строка с `Lock`, без номера, удаления,
  drag и подписи Final action. Она не входит в `profile.interfaces`;
  terminal-поведение хранится в `on_unavailable`.

## 10. Граница с маршрутизацией backend

UI редактирует конфигурацию; доступность и failover определяет backend.
Не добавляй сетевые пробы и таймеры переключения. Настроенный первый интерфейс
не доказывает доступность и не заменяется runtime-резервом в поле `interface`.

Сохраняй прямой выбор и профиль через `RouteSelect`: `interface/<name>` и
`profile/<id>` — разные идентичности; название не заменяет ID.
Импорт/экспорт через `profiles-data.ts` сохраняет определения, переназначает
конфликтующие ID и отвергает отсутствующие ссылки.

## 11. Доступность и локализация

Используй реальные controls и Bits UI. Tooltip не заменяет доступное имя кнопки;
бледность/`inactive` не заменяет `disabled`. Обработчик тоже учитывает busy/disabled.
Сохраняй клавиатуру, видимый фокус, Escape и возврат фокуса. Не маскируй ошибки
тотальным `stopPropagation`/`preventDefault` и подавлением a11y предупреждений.
Проверяй кликабельность popup поверх соседней и у свёрнутой панели.

Весь новый текст, включая placeholder, tooltip и aria-label, проводи через `t()`
из `src/data/locale.svelte.ts`; перевод ключа добавляй в `src/locales/ru.json`.
Проверяй обе локали. Пользовательские имена, ID и интерфейсы не переводи.
Внешние строки экранируй; `{@html}` требует безопасной обработки.
Не логируй токены и полную конфигурацию ради UI-отладки.

## 12. Большие списки

Сохраняй пагинацию, staged rendering и поиск. Не рендери, не копируй и не
сериализуй всю коллекцию на каждый ввод одного поля. Проверяй вложенные поиски
на реальном размере данных; не усложняй маленькие профили кэшированием.
Не обновляй зависимости попутно; ресурсы собирай локально без новых UI/font CDN.

## 13. Форматирование и команды

Следуй Prettier проекта: два пробела, LF, semicolons, настроенный порядок импортов.
Форматируй изменённые файлы; `npm run format` переписывает многое и не нужен
автоматически для небольшой задачи.

Команды из `src/frontend/` выбираются по области изменения:

```sh
npm ci
npm run check
npm run build
npm run format:check
npm run test:unit
npm run test:e2e -- profiles.spec.ts
```

Без фильтра E2E запускает всю suite. Браузер: `npx playwright install chromium`.
`format:check` охватывает `src`, `tests`, `dev`; корневые файлы проверяй отдельно,
например `npx prettier --check AGENTS.md`. Наличие CI-gate проверяй в workflow.

Для ручной разработки смотри `README.md` и `dev/`; пользовательскую конфигурацию
не коммить как fixture.

## 14. Соразмерные проверки

- Документация: сверка с исходниками, Markdown и diff. Сборка и тесты приложения не нужны.
- Локальный UI: форматирование, check/build для исходников, desktop/mobile просмотр;
  существующий профильный E2E, если затронуты органы управления.
- Общий компонент, навигация, DnD, глобальный CSS: соответствующие взаимодействия;
  вся frontend-suite, если область влияния действительно широкая.
- Состояние, save, ID, валидация, payload, импорт/экспорт: unit и браузерные
  сценарии результата, включая важные ошибки и повторные действия.
- Реальное API/persistence/failover: соответствующие проверки backend.

Используй ближайший тест. Для поведения/бага проверяй наблюдаемый результат,
payload и сохранность состояния. Для отступа не нужны новые тесты, читающие
исходник или повторяющие CSS. Устаревшее ожидание при намеренном UI-изменении
обновляй узко, сохраняя смысл. Предпочитай role/name/label и ожидание состояния,
а не внутренности компонента и произвольные длинные задержки.

Существующие наборы в `tests/e2e/`: `profiles.spec.ts`, `persistence-retry.spec.ts`,
`dnd.spec.ts`, `popovers.spec.ts`, `accessibility.spec.ts`, `header.spec.ts`,
`large-groups.spec.ts`, `large-subscriptions.spec.ts`. Для чистой логики смотри
`tests/unit/profiles-data.test.ts`, `tests/unit/applied-save.test.ts` и payload/store tests.

Базовые размеры просмотра — `1280 × 900` и `390 × 844`. Проверяй доступность
Add/Save/Delete, обрезание, переносы и горизонтальную прокрутку; дополнительные
ширины/длинные строки — при соответствующем риске. Для DnD проверяй порядок,
допустимые цели и неподвижный blackhole; для save — повтор, смену вкладки и reload.

Не приписывай проверкам лишнего:

- Unit suite использует `--no-check` и не заменяет `npm run check`.
- `tests/mocks/setup-svelte-runes.ts` не доказывает настоящую реактивность/DOM/focus.
- Playwright и `playwright.c-backend.config.ts` используют API-моки `page.route`;
  они не доказывают реальную маршрутизацию и запись конфигурации.
- Мобильный viewport Chromium не является проверкой Safari/iOS.
- Screenshot/trace/video могут быть выключены. Сообщай о визуальной проверке
  только после фактического просмотра.

## 15. Чистый diff и завершение

Для внешнего вида не добавляй CI jobs, метрики, coverage thresholds, browser
projects и инфраструктуру тестов. Не ослабляй проверки ради зелёного результата.
Общее изменение сопровождай проверкой затронутых сценариев.

Проверь `git diff --check`, список файлов и diff. Исключи случайные build output,
временные fixtures, скриншоты, credentials и сгенерированные декларации.
Удаляй только свои временные файлы.

После достаточной проверки расширяй её для конкретного риска или обязательного
gate. Если сообщаешь о CI, проверяй отправленный SHA. В результате укажи изменения,
причину, переиспользованные компоненты, реальные проверки, commit и ограничения.
