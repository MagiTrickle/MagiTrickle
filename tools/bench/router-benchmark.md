# Сравнение пакетов на реальном роутере

`router_dns.py` запускает неизменённые бинарники пакетов на роутере через
SSH, а `dnsload` выполняет запросы локально на этом же устройстве. Нет
`dnsstub`: используются публичные домены из `router-domains.txt` и штатный
DNS роутера. Это контролируемая нагрузка с реальными DNS-ответами, а не
запись трафика пользователей и не измерение скорости интернет-соединения.

## Подготовка

Нужны Entware с `chroot`, bind mounts, `iptables-save`/`iptables-restore`,
SSH-доступ root и свободные порты 13553 (DNS) и 18080 (HTTP на loopback).
Каталог `/tmp/mt-router-bench` должен быть новым. Скрипт подготовки не
устанавливает пакеты и не останавливает рабочий сервис.

1. Скачайте оригинальный пакет **для архитектуры роутера**, проверьте его
   SHA-256 по официальному релизу и извлеките бинарник:

   ```sh
   mkdir -p /tmp/original-package
   tar -xzf magitrickle.ipk -C /tmp/original-package
   tar -xzf /tmp/original-package/data.tar.gz -C /tmp/original-package
   ```

   В опубликованном прогоне использован
   [официальный пакет 0.8.2-2 для mipsel-3.4_kn](https://github.com/MagiTrickle/MagiTrickle/releases/tag/0.8.2-rev2).
   URL и контрольная сумма зафиксированы в `packages.json` результатов.
   Проверяется именно пакетный бинарник, включая применённый издателем UPX.

2. Соберите **только генератор нагрузки** на компьютере. Для использованного
   MT7621 (little-endian MIPS, softfloat):

   ```sh
   cd tools/bench
   go test -race ./dnsload
   CGO_ENABLED=0 GOOS=linux GOARCH=mipsle GOMIPS=softfloat \
     go build -trimpath -ldflags='-s -w' -o /tmp/dnsload ./dnsload
   ```

   Это не команда сборки mt-c: его бинарник должен происходить из пакета
   или корректной целевой сборки с Entware glibc и зависимостями feed.

3. Загрузите извлечённый оригинальный бинарник и скрипт подготовки. Можно
   сравнивать с установленным mt-c, не меняя его рабочий конфиг:

   ```sh
   scp -O -P 222 /tmp/original-package/opt/bin/magitrickled \
     root@172.16.3.3:/tmp/mt-original
   scp -O -P 222 tools/bench/router_prepare.sh root@172.16.3.3:/tmp/
   ssh -p 222 root@172.16.3.3 \
     '/opt/bin/sh /tmp/router_prepare.sh /tmp/mt-router-bench /tmp/mt-original /opt/bin/magitrickled'
   scp -O -P 222 /tmp/dnsload root@172.16.3.3:/tmp/mt-router-bench/
   ```

4. Сохраните `uname`, `/proc/cpuinfo`, `/proc/meminfo`, версию Entware,
   версии/хеши бинарников, commit инструментария, версию Go и параметры запуска.
   Найдите **AT_CLKTCK (17)** в `od -i /proc/self/auxv` на роутере.
   В данном прогоне это **100**, но подставлять это число без проверки нельзя.
   PSS недоступен, если ядро не предоставляет `smaps`/`smaps_rollup`.

## Запуск и результаты

Из корня репозитория:

```sh
ssh -M -N -f -o ControlPath=/tmp/mt-bench-ssh.sock -o ControlPersist=600 \
  -p 222 root@172.16.3.3
python3 tools/bench/router_dns.py --clk-tck 100 \
  --control-path /tmp/mt-bench-ssh.sock --output /tmp/router-results
python3 tools/bench/router_summary.py /tmp/router-results/results.jsonl
```

По умолчанию: 100/1000/10000 namespace-правил; 32 настоящих домена
распределены по всему списку правил, остальные правила — `.bench.invalid`.
Запрашиваются только настоящие домены. Конфиги одинаковы для обоих пакетов;
их SHA-256 записывается в каждой строке измерений. Число и тип правил
контролируются тестом, это не копия пользовательского конфига.
Конфиги создаются генератором при запуске и остаются локальными артефактами.
В репозиторий сохраняются методика, измерения и контрольные суммы;
YAML и архивы конфигов не публикуются.

- Сначала измеряется прямой upstream `127.0.0.1:53`: UDP/TCP, по 3×20 с.
- Прогоны демонов идут попарно; порядок меняется Go→C, C→Go, Go→C.
  Перед каждым прогоном процесс запускается заново, проходит probe,
  5 с простоя и 3 с непрерывного прогрева.
- Capacity: 10 клиентов без пауз, UDP/TCP, по 3×20 с на каждую версию.
  UDP — постоянный сокет на клиента; TCP — соединение на каждый запрос.
- Paced: 1000 правил, UDP, суммарно 20 запросов/с, по 3×30 с на версию.
  Это выбранная умеренная нагрузка, а не измеренная нагрузка домашней сети.
- RPS считается по успешно проверенным ответам и фактической длительности
  генератора, включая завершение запросов после установленного дедлайна.
  Проверяются ID, вопрос, NOERROR, отсутствие TC и наличие A-ответа;
  SERVFAIL/NXDOMAIN/пустые ответы не считаются успехом. Проверка не заменяет
  функциональные differential-тесты и не проверяет достоверность DNS.
- CPU демона: разность `utime+stime` процесса, делённая на AT_CLKTCK и
  интервал `/proc/uptime`. Снимки и нагрузка выполняются одной SSH-командой,
  поэтому задержка SSH не входит в измеряемый интервал. 100% = один
  логический CPU; это не суммарная нагрузка всего роутера.
- Задержка измеряется от начала попытки обмена до проверки ответа, включая
  установку TCP-соединения. CPU генератора измеряется отдельно через
  `getrusage`. RSS/VmHWM/число потоков берутся из `/proc/PID/status`. RSS включает общие страницы
  библиотек; это не объём памяти, который освободится при остановке процесса.
- Итог — медиана и min–max трёх прогонов; ошибки и таймауты суммируются.
  Таймауты входят в счётчик ошибок. Задержки относятся к успешным ответам.
  Probe и прогрев сохраняются отдельно, в итоговые нагрузочные цифры не входят.

## Границы сравнения

Оба демона работают в одинаковом chroot с библиотеками и утилитами роутера.
Конфиг, socket и PID-файлы приватные. Префиксы netfilter — `MTB_`/`mtb_`;
DNS remap отключён. Группа **включена** у обеих версий: выполняются
сопоставление правил и записи реальных ответов в отдельные `mtb_` ipset.
`netfilter.disableIPv4: true` и `disableIPv6: true` отключают iptables,
policy rules и маршруты, оставляя тестовые множества непривязанными
к рабочему трафику. Выключать саму группу нельзя: C исключает её из
сопоставления, тогда как Go продолжает перебор правил; это даёт перекос.
HTTP включён на loopback для совместимости с оригинальным пакетом; WebUI-нагрузка не измеряется.

Рабочий mt-c, штатный DNS и остальные службы остаются запущенными.
Governor, affinity и фоновые службы не меняются. Генератор делит CPU с
демоном, поэтому capacity-RPS ограничен также генератором и upstream.
Это измерение конкретной связки на работающем устройстве; переносить
абсолютные цифры на другое железо, интернет-канал или обычный трафик нельзя.
Малые различия внутри разброса не доказывают преимущества. Измеряется
обновление ipset, но нет измерения полного пути маршрутизации через iptables,
холодной рекурсии DNS, смешанных/regex-правил, пиков памяти при обновлении подписок или длительного soak.

Графики README воспроизводятся отдельно (нужен `matplotlib`):

```sh
python3 tools/bench/router_plot.py /tmp/router-results/results.jsonl --output img
```

График CPU показывает процессорное время демона, делённое на число
успешных ответов; в него входит работа над запросами, завершившимися ошибкой.

## Действующий набор правил

`--live-rules /path/to/private-config.yaml` заменяет сгенерированную матрицу
одной UDP-серией 20 запросов/с, 3×30 с. Для этого режима нужен PyYAML.
Используются включённые группы и сохранённые правила включённых подписок.
Типы, значения, порядок и флаги правил сохраняются; идентификаторы и имена
обезличиваются. Приложение использует тот же тестовый upstream/порт,
blackhole-интерфейсы, отключённые iptables и remap. URL и interval подписок
пустые/нулевые: обновление списка во время теста исключено. Профили,
учётные данные и прочие настройки приложения не копируются.

После probe режим ждёт три последовательных интервала по 5 с с CPU демона
ниже 10% (максимум 180 с), чтобы не мерить начальную синхронизацию subnet
правил. Далее идут обычные простой, прогрев и измерение. Прямой upstream
измеряется основной матрицей, не повторяется этим режимом. Состав правил и
SHA-256 конфига публикуются, значения правил/пользовательский YAML — нет.
Это воспроизведение набора правил с изменёнными настройками запуска и
фиксированным публичным DNS-корпусом, а не тест неизменённого production
конфига или запись пользовательского трафика.

```sh
python3 tools/bench/router_dns.py --clk-tck 100 \
  --control-path /tmp/mt-bench-ssh.sock --live-rules /path/to/private-config.yaml \
  --output /tmp/live-rule-results
python3 tools/bench/router_summary.py /tmp/live-rule-results/results.jsonl
```

Запускайте последовательно с основной матрицей: оба режима используют один
тестовый порт и chroot. Для конфиденциального исходного YAML используйте
приватный файл с правами 0600 вне репозитория.

## Плотная кривая и большие конфиги

Дополнительные UDP-точки между исходными 100/1000/10000 правилами:

```sh
python3 tools/bench/router_dns.py --clk-tck 100 \
  --control-path /tmp/mt-bench-ssh.sock --udp-only --skip-upstream --memory-guard \
  --rules 200 500 2000 5000 20000 50000 100000 --output /tmp/curve-extra
python3 tools/bench/router_summary.py /tmp/router-results/results.jsonl /tmp/curve-extra/results.jsonl
python3 tools/bench/router_plot.py /tmp/router-results/results.jsonl /tmp/curve-extra/results.jsonl --output img
```

Графики используют логарифмические шкалы обеих осей и соединяют реальные
медианы, без расчётных промежуточных точек или экстраполяции. Третий график —
RSS после нагрузки. VmHWM и VmSwap вынесены в таблицы; отсутствие VmSwap
в старых строках обозначается «—», а не нулём.

На использованном роутере нет memory cgroups, но есть штатный zram-swap.
`--memory-guard` меняет только `oom_score_adj` тестового дочернего процесса
на +1000 ([назначение параметра](https://www.kernel.org/doc/html/latest/filesystems/proc.html#proc-pid-oom-adj-proc-pid-oom-score-adj-adjust-the-oom-killer-score)).
Отдельный процесс раз в секунду завершает тестовый PID, если MemAvailable
ниже 16 MiB или SwapFree ниже 64 MiB. Это предохранитель для рабочего
устройства, а не cgroup-лимит или гарантия изоляции памяти. Production
параметры и настройки swap не меняются. Достигнутый предел публикуется как
неудавшийся запуск, без нулевого или расчётного RPS. Контроль сам расходует
небольшую долю CPU; первоначальные три точки получены без него.

Одна из целей крупных точек — обнаружить рост памяти и возможное влияние
swap. Нельзя интерпретировать RSS как всю память приложения, особенно если
VmSwap ненулевой. Пиковое VmHWM включает загрузку YAML и построение правил.

Завершив тест, убедитесь, что тестовые демоны остановлены, и снимите только
созданные для теста bind mounts, в обратном порядке:

```sh
ssh -p 222 root@172.16.3.3 '
  for dir in /lib /bin /dev /sys /proc /opt/sbin /opt/lib; do
    umount "/tmp/mt-router-bench/root$dir" || exit 1
  done'
ssh -S /tmp/mt-bench-ssh.sock -O exit -p 222 root@172.16.3.3
```

Не удаляйте дерево chroot до успешного unmount: там находятся bind mounts
рабочих каталогов роутера. При прерывании `router_dns.py` отправляет TERM
только своему PID; при потере SSH проверьте тестовые процессы отдельно.
